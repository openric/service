# 2026-05-25 — OpenRiC service v0.9.1 + v0.9.2

Two releases shipped in one session.

## v0.9.1 (`e344408` + `561b848`) — Spec-canonical semantic URIs + spec_version refresh

- **New: `/id/{kind}/{id}` semantic URI resolver** (`packages/ahg-ric/routes/web.php`). Implements [openric-spec viewing-api §3.1](https://ric.theahg.co.za/reference/) — 13 kinds (record, record-set, record-part, agent, person, corporate-body, family, mechanism, place, rule, activity, instantiation, function), content-negotiates `Accept`, 303s to either `/api/ric/v1/{collection}/{id}` (machine clients) or the human view (browsers). `Vary: Accept` set; numeric ids on slug-keyed collections resolved via the `slug` table; `corporate-body` falls back to `/repositories/...` when the entity lives in the ISDIAH repository table rather than the actor table.
- **Spec version tracker** bumped 0.37.1 → 0.38.0 in `$openricConformance` (`packages/ahg-ric/routes/api.php`). v0.38.0 is additive on top of v0.37.1; six normative profile claims unchanged.
- **Deployment plumbing** found during ship: `packages/ahg-ric/` is a composer path repo with `"symlink": false`, so `composer install` is required after package edits to sync `vendor/ahg/ric`. The `ric.theahg.co.za` nginx vhost is a per-path allowlist (no Laravel catchall), so the new `/id/...` route needed a matching `location ~ ^/id(/|$) { try_files $uri $uri/ /index.php?$query_string; }` block in `deploy/ric.theahg.co.za.conf`. Both deployment touchpoints are now in the deploy/ tree and the README.

## v0.9.2 (`cee59df`) — Detail-endpoint regression remediation

Conformance probe (re-run for the first time since v0.9.0) flagged **3 failures of 24**. Investigation showed **4 of 8 detail endpoints had been 500'ing for 35 days** since commit `0c786376` (2026-04-20). Root causes:

1. **`RicSerializationService` missing 15 helpers** + `serializeRepository` entirely + corrupted `serializeFunction` / `exportRecordSet` bodies (copy-pasted code referencing undefined `$repo`/`$thing`/`$repositoryId`/`$ricRepo`). Ported the missing pieces from Heratio's `ahg-ric` package per `feedback_copy_from_heratio`, adapted to OpenRiC's v0.9.0 RiC-O 1.1 conventions (`rico:ContactPoint` not `rico:Contact`; contact predicates moved to `openricx:`; date wrappers using `openricx:hasDateRangeSet` where appropriate; `Schema::hasTable` / `hasColumn` guards on optional ICIP / personal-data / occupation tables).
2. **`getActivitiesForFunction` schema drift** — Heratio assumed a `function_id` column on `ric_activity`; OpenRiC schema has no such column (the link lives in the `relation` table). Added a `Schema::hasColumn` guard so the method returns `[]` rather than 500ing. Wiring the actual function ↔ activity link through `relation` is left for a follow-up.
3. **`listAgents` emitting slug-less actor rows** — first agent in `/agents` had `@id: https://ric.theahg.co.za/actor` (no slug, null name). Probe extracted `actor` as the id → 404 on detail dereference. Added `whereNotNull('slug.slug')` filter to the list query.

### The masking pattern (the actually-useful lesson)

The real exceptions on the failing endpoints were *clear* (`Error: Call to undefined method getDatesForRecord()`). But we never saw them. The error renderer's Blade `tempnam()` call was failing because the **`ProtectSystem=full` drop-in for OpenRiC was never installed**, so every real exception got re-thrown as `ErrorException: tempnam(): file created in the system's temporary directory` before reaching the log. The chain:

```
detail endpoint throws real exception → exception handler renders HTML page via Blade
  → BladeCompiler::compile → Filesystem::replace → tempnam(dirname, basename)
  → ProtectSystem=full blocks write → tempnam falls back to /tmp + emits PHP warning
  → HandleExceptions escalates warning to ErrorException → THAT gets logged and shown
```

The original exception was **never** logged. The log was empty for the daily file because Monolog couldn't open it (same ReadOnly issue). The user-visible 500 page was always the same generic tempnam error regardless of what actually broke.

When you see `tempnam(): file created in the system's temporary directory` on a Laravel app under `/usr/share/nginx/`, that is **always** the ProtectSystem-drop-in-missing signature. Fix the drop-in first (`/etc/systemd/system/php8.3-fpm.service.d/<app>-storage.conf` granting `ReadWritePaths=` for `storage/` and `bootstrap/cache/`), then re-trigger to see the real error. Documented in the global `CLAUDE.md`; OpenRiC-specific drop-in now committed at `deploy/systemd/openric-storage.conf`.

### Why the regression stayed hidden 35 days

Three independent failures conspired:

1. **ProtectSystem drop-in missing** → all real exceptions masked behind generic tempnam errors → no actionable signal.
2. **Conformance probe never re-run after v0.9.0** → no integration coverage exercised. Status board said "advisable when a curious reviewer asks" — that's too weak a trigger.
3. **Probe coverage gap** → `probe_show_first` runs detail-show probes for only records/agents/repositories. Functions and 4 other entity types are list-only in the probe. Tracked as A1.7.

The unit test suite (`packages/ahg-ric/tests/`) is near-empty (4 skipped tests) and is not currently a substitute. The probe is the closest thing to integration coverage we have — and it wasn't being run.
