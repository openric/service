# 2026-05-25 — OpenRiC service v0.9.3: Production participant backfill

Third release of the day. Follows from the A4 audit (228 Production activities; 183 missing `performed_by`).

## What shipped

- **New Artisan command** `openric:backfill-production-participants` at `packages/ahg-ric/src/Console/Commands/BackfillProductionParticipants.php`. Idempotent, transactional, dry-run-first. Registered in `AhgRicServiceProvider`.
- **Live backfill executed** against the production database. 13 `performed_by` relation rows inserted. Coverage: **45 → 58 of 228 Production activities (19.7% → 25.4%)**.
- Each new row tagged `ric_relation_meta.certainty = 'derived'` + `evidence` field pointing to the 2026-05-25 audit memo.

## The audit (recap)

Two paths produced safe candidates (archivally-grounded, not database-artifact-derived):

1. **Creator-event** — activity has `results_from` → record, record has `event.type_id = EVENT_TYPE_CREATION (111)` + non-null `actor_id`. 8 activities, all pointing at one creator agent.
2. **Inverse-encoded** — actor row points AT activity via `has_creator`/`has_accumulator` relation. 5 activities.

Discarded paths:
- **`openric_audit_log.user_id`** (6 activities matchable) — names the archivist who edited the row in 2026, not the historical performer. Backfilling this would invent provenance.
- **`event` rows directly on the activity** (0 matches) — events table is record-only.

## What did NOT change

- **The `provenance-event` profile is still not claimed.** Even at 25.4% coverage, well below conformance threshold. The bottleneck is archival truth: 137 of the 170 unfilled activities are pre-1950 material where the creator is unknown to the archive. The fix is **spec-level prose refinement**, not more backfill. Issue draft at `openric-spec/docs/issues/provenance-event-creator-unknown.md`.
- **The 4 true orphan activities** (no `performed_by`, no `results_from`, no inverse) are demo / test content: "Creation" (2025-12), "Giza Pyramid Organization" (×2 — boat-on-display demo), "UFAL" (2026-05-17 stub). They surface in the API as `rico:Activity` without participants or results — which is graceful, not broken. No action needed; they'll get curated through the UI when relevant.

## How to reverse if needed

```sql
-- Identify the 13 backfilled rows:
SELECT r.id, r.subject_id, r.object_id, rm.evidence
FROM relation r JOIN ric_relation_meta rm ON rm.relation_id = r.id
WHERE rm.certainty = 'derived' AND rm.dropdown_code = 'performed_by';

-- Reverse (cascading on object PK):
DELETE FROM object WHERE id IN (
  SELECT relation_id FROM ric_relation_meta WHERE certainty='derived' AND dropdown_code='performed_by'
);
```

The `certainty='derived'` tag + `evidence` field were specifically designed so this is trivially reversible — no need to grep git history.

## Strategic implication

The `provenance-event` profile claim is now blocked solely on **spec-prose refinement**, not data deficit. Once the openric-spec issue is filed, discussed, and resolved (probable resolution: profile allows `rico:Production` without `rico:hasOrHadParticipant` when the underlying record claims no creator), the reference service can add `provenance-event` to its claimed-profiles list in a follow-up service release. That moves the conformance probe from 6 → 7 of 7 normative profiles claimed (excluding `sparql-access` Draft).
