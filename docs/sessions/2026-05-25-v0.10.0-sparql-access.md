# 2026-05-25 — OpenRiC service v0.10.0: SPARQL Access profile claimed

Fourth release of the day. Minor version bump (first new profile claim since the original six).

## What shipped

- **New `SparqlController`** at `packages/ahg-ric/src/Http/Controllers/SparqlController.php`. A proper SPARQL 1.1 Protocol proxy to the backend Fuseki triplestore.

- **OpenAPI** updated with full GET + POST entries for `/sparql` and `GET /sparql/info`, including realistic 4xx/5xx response codes.

Conformance probe (against openric-spec v0.38.3): **30/30 PASS**.

## What the previous endpoint was doing wrong

The `LinkedDataApiController::sparql` method (live since v0.8) was a 60-line passthrough that:

1. **Wrapped Fuseki's response in a non-canonical envelope.** `{"sparql": query, "@context": {...}, "results": {...}}` instead of canonical `{"head": {"vars": [...]}, "results": {"bindings": [...]}}`. SPARQL clients can only parse the canonical form; the envelope made the endpoint useless to actual SPARQL tooling.
2. **Silently masked backend errors as HTTP 200.** When Fuseki returned 400 for a malformed query or an UPDATE attempt, the proxy stuffed `{"error": ..., "http_code": 400}` into the wrapped envelope and returned HTTP 200. Clients checking the status code thought the query had succeeded.
3. **Didn't honor Accept.** Hard-coded to `application/json`. No way to get the canonical SPARQL Results JSON / XML / CSV / Turtle / JSON-LD that the SPARQL 1.1 Protocol requires.
4. **No POST support.** SPARQL queries longer than the URL limit (browsers cap around 2 kB, nginx config-dependent) could not be sent.
5. **No `/sparql/info`.** No way for a consumer to discover the dataset's triple count, vocabularies, or license.
6. **No SPARQL Update rejection at the proxy layer.** Fuseki's `/sparql` endpoint is read-only by default, so writes weren't actually mutating the graph (good), but the proxy returned the Fuseki parser error wrapped in an HTTP 200 envelope (bad).

The new controller fixes all six.

## SPARQL Update rejection — details

A SPARQL query and a SPARQL Update look superficially similar — both can contain keywords like `INSERT` or `DELETE`. The naive approach (substring match on `INSERT`) breaks legitimate `SELECT ?x WHERE { ?x ex:label "DELETE this row" }` queries. The controller does it carefully:

1. Strip block comments (`/* ... */`) and line comments (`# ...`).
2. Strip triple-quoted literals (`"""..."""`, `'''...'''`).
3. Strip single-quoted literals (`"..."`, `'...'`).
4. Then match `\b(INSERT|DELETE|CLEAR|DROP|CREATE|LOAD|COPY|MOVE|ADD)\b` case-insensitively.

Verified manually with `SELECT ?s WHERE { ?s ex:name "DELETE this row" } → HTTP 200`. Verified `INSERT DATA { <ex:s> <ex:p> "evil" } → HTTP 403 + application/problem+json + type=https://openric.org/errors/update-not-permitted`.

## The probe that almost-passed

The patched openric-spec v0.38.3 probe is the companion patch. The previous probe's `/sparql` test had two bugs:

1. URL contained raw `{`, `?`, `}` characters; curl was treating `{...}` as a glob and `?` as a query-string delimiter, mangling the URL before transmission.
2. Predicate was a bare `.` (any non-null JSON), accepting the non-canonical wrapped envelope as success.

Both bugs hid the v0.8-era endpoint's non-conformance for months. With the v0.10.0 controller emitting canonical SPARQL Results JSON, the old probe started failing on the *mangled URL*, which is what surfaced the probe bugs. Patched in spec v0.38.3 (URL-encoded via `jq -sRr @uri`, and the predicate now asserts `(.head.vars | type) == "array"`).

## Operational notes

- **Backend:** Fuseki/Jena running on localhost:3030 against the `openric` dataset (per `config('ahg-ric.fuseki_endpoint')` default). The graph contains ~7,192 triples as of 2026-05-25, computed via `SELECT (COUNT(*) AS ?n) WHERE { ?s ?p ?o }` and surfaced through `/sparql/info`.
- **License declaration:** the void:Dataset description currently declares `dcterms:license <https://creativecommons.org/licenses/by/4.0/>`. This may need to change once the reference dataset's actual licensing is confirmed; configurable via `config('ahg-ric.dataset_license')`.
- **Rate limit:** Laravel's `throttle:60,1` middleware. Hitting the limit returns `HTTP 429` from Laravel's stock throttler — currently NOT in `application/problem+json` shape because the throttle middleware predates the RFC 7807 helper. Followup: wire the throttler to emit problem+json on 429 (small patch, separate release).
- **Auth:** none — public-read posture. Future server-deployments holding sensitive metadata should declare `authenticated-read` or `tenant-restricted` per the profile and add a scoped API-key middleware.
