## Canonical identifiers in a browser (defect)

The plan found, and I confirmed on ric.theahg.co.za with `Accept: text/html`:

| Address | Before | From v0.18.8 |
|---|---|---|
| `/id/place/912324` | 303 to `/admin/ric/entities/place/912324`, then 404 | 303 to `https://viewer.openric.org/?start=/place/912324` |
| `/id/record/egyptian-boat` | 303 to `/egyptian-boat`, then 404 | 303 to `https://viewer.openric.org/?start=/informationobject/egyptian-boat` |
| `/id/function/910067` | 303 to `/admin/ric/entities/function/910067`, then 404 | 303 to the record page, as above |
| `/id/function/1` | 303 to `/admin/ric/entities/function/1`, then 404 | 404: id 1 is AtoM's hidden root object |
| `/id/record/768` (a draft) | 303 to a URL naming its slug | 404 |
| `/place/912324` (short form) | 303 to the record page | unchanged |

: Browser dereference of identifiers, 26 November 2026

Data clients (`Accept: application/ld+json`) were already sent to the API and still are. The viewing API (§3.1) asks only for `Vary: Accept` and a 303 to a representation. It does not name the browser destination, so the fix uses the one the short form already used.

The three-part resolver (`/{instance}/{type}/{key}`) had the same browser branch and the same fix. nginx does not pass it to the app on this host, where it answers 404.

`IdentifierResolutionTest` covers all thirteen kinds for browsers and data clients, the match with the short form, and drafts on both resolvers. It runs in CI.

The conformance probe passed while this was broken. Whether it should follow identifiers as a browser is held for the probe-coverage item of this week's plan.

## Sign-in sweep (security)

The plan's sign-in sweep, done on 26 November 2026. `php artisan route:list` gives 314 routes. I tested every route that is not meant to be public, anonymously and read-only, through nginx and through the app itself (the kernel, without nginx). Write routes were checked from their middleware and in a scratch copy, never by sending a write to the live service.

| Finding | On ric.theahg.co.za | Inside the app | From v0.18.9 |
|---|---|---|---|
| SPARQL `SERVICE` clause | A visitor's query made Fuseki send a GET to `http://127.0.0.1:9/`, and the error echoed the address | Same | 403 `service-not-permitted` |
| SPARQL update check: a `#` inside an IRI hid the rest of the line, and `/* */` was stripped, though SPARQL has no block comments | Fuseki's query-only service still refused updates | Same | Literals, IRIs and comments are read in one pass |
| SPARQL backend failure (5xx) | The backend's message, internal addresses included, went to the caller | Same | A fixed message; a parse error (400) still explains itself |
| The AtoM-compatible API, `/api/v1/*` and `/api/*` (records, actors, donors, accessions, physical and digital objects, terms, pending counts) | 404 from nginx | Open to anyone, drafts included (`/api/v1/informationobjects/mobrey-family-archive` answered 200) | An admin-scope key or a signed-in session |
| `/api/v2` privacy requests, breaches and audit log | 404 from nginx | Any read key | An admin-scope key or a signed-in session |

: Sign-in sweep findings, 26 November 2026

Checked and in order: OAI-PMH lists 579 records, the same as the published total, and a draft answers `idDoesNotExist`. A published record set's export leaves out its hidden descendants in all three formats (`PublishedOnlyTest`). Key requests wait for an operator, so nobody can give themselves a key. `POST /ask` and `POST /wizard/suggest` return no record data. The clipboard routes work on the caller's own session.

Not changed: `/api/v2/webhooks`, `/events` and `/sync/changes` stay on the read scope, which an operator grants by hand. Fuseki itself still allows `SERVICE`; turning it off there as well (`arq:httpServiceAllowed false`) is a host change, held for Dr Johan Pieterse.

`SignInSweepTest` covers every route above, the preflight, and SPARQL with the keywords in literals, IRIs and comments. Each of its four tests fails on the old code.
